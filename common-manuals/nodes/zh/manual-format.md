# 用户手册格式

用户手册不是给人读的文章，是给模型反复读、被机械增改的**上下文**。格式不对，每次维护都会变成重写；每次重写都会漂移。

这一页规定「项目索引」「价值偏置」这类**由 Agent 维护的用户手册**该长什么样。用户手写的手册尊重他的风格，不强行套。

## 六条硬规定

1. **一行一条，只讲一件事**：字段用 ` | ` 分隔（半角竖线，两侧各一个空格），顺序固定，不嵌套、不用子项目符号。
2. **每条以可检索的键开头**：索引行以名称开头，偏置行以场景开头。找到那一条是字符串匹配，不是通读全文。
3. **日期一律 `YYYY-MM-DD`**，只到日；需要精确时刻才写时分。
4. **只写可判定的判据**，不写背景故事。「因为上次踩过坑，所以…」删掉，留「当 X 时做 Y」。
5. **增改，不重写**：默认追加一行或就地替换那一行；要重组整份手册（改字段、改分节、批量删），先问用户。
6. **标来源**：行尾 `(YYYY-MM-DD · 出处)` 或独立一列。能被推翻的前提是能追溯。

## 骨架

```text
# <手册名>

> 一句话用途 + 字段口径（字段顺序固定；不确定写 ?）

<条目区：一行一条>
```

- 标题就是手册名，与 `name` 一致，不要另起别名。
- 那行 `>` 既是给人看的口径，也是给你看的：改字段顺序前先改它。
- 条目区不分组、不加小标题；超过约 60 行再按场景分节，节标题用二级标题。

## 收敛

- 手册要**收敛**，不是只增不减：同类条目超过 3 条就合并成一条更一般的。
- 失效条目**直接删**，不要留「已废弃」——残留条目会继续被读进上下文，比没有更坏。
- 约 60 行是上限；到上限先合并，再考虑拆子手册。

## 与 Note / Archive 的分工

- **Note**：这一轮要达成的目标与 TODO，做完就划掉。
- **Manual**：跨轮次、跨压缩都要在的判据与事实——本页讲的就是它的格式。
- **Archive**：历史，只追加、不修改。
- 一句话：做完就消失的写 Note，长期有效且要收敛的写 Manual，只用来复盘的写 Archive。

## 建手册的时机

- 需要时直接建：钩子真的触发了（有第一个项目要记、有第一条偏置要记）再建，不预建空手册。
- 建的时候一句话告知用户，让他知道这份手册存在、可以改、可以删。
- 用户删掉的手册不要自动重建。
